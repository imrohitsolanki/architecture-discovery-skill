# Conventions for the generated code

Read this before writing the first `.tf` or `.hcl` file, and again when a reviewer
asks why something is shaped the way it is.

These are the conventions a Terraform reviewer expects to find without being told.
Four of them are checked by the `conventions` gate; the rest are judgement, and a
gate guessing at them would produce findings nobody can act on.

## Checked by the `conventions` gate

| Rule | What it prevents |
|---|---|
| Every `variable` has a `description` | The variables file is the module's interface. An undescribed input is one the next person guesses at, and a guess about an input is applied infrastructure. |
| Every `variable` has a `type` | Untyped is `any`, so a string arriving where a list was meant fails deep inside the module rather than at the call that caused it. |
| Every `output` has a `description` | An output is a published interface. Whoever consumes it sees the name and nothing else. |
| No `provider` block in a child module | It cannot then be used with `for_each` or `count`, and removing one later is a breaking change for every caller. Providers belong to the root module, or are generated by Terragrunt from `root.hcl`. |

## Checked by the `guardrails` gate

Thirteen secure defaults §6 of the interview asserts, checked against the code. The
id in brackets is what a waiver names: where the specification recorded a deviation,
put the id in the waiver's `control` field and the gate reports the finding instead
of blocking it. Matching is literal, so the spelling matters.

They come in two halves, and the second half is the one that is easy to forget.
Eight fire on something **present** that should not be — a public port, a wildcard
policy, encryption switched off. Five fire on something **absent** that should be
there. A generated stack fails the second way far more often than the first: nothing
on the page is wrong, a required sibling resource is simply missing, and it reviews
clean.

| Check | Fires on |
|---|---|
| `public-admin-ingress` | `0.0.0.0/0` or `::/0` into an `ingress` block covering SSH, RDP, a database port, or all ports |
| `public-data-store` | `publicly_accessible = true`, a `public-read` ACL, a public access block attribute set to `false` |
| `unencrypted-storage` | `storage_encrypted`, `encrypted`, `at_rest_encryption_enabled` and friends set to `false` |
| `wildcard-iam` | a policy with both `Action = "*"` and `Resource = "*"` |
| `static-credentials` | a literal `access_key`, `secret_key`, `client_secret` or `password` |
| `unrestricted-mock-outputs` | `mock_outputs` with no `mock_outputs_allowed_terraform_commands` |
| `key-rotation-disabled` | `enable_key_rotation = false` |
| `secret-in-variable-default` | a variable named like a secret with a literal `default` |

And the five that fire on an absence:

| Check | Fires on |
|---|---|
| `vpc-without-flow-logs` | an `aws_vpc` or `azurerm_virtual_network` with no flow log anywhere in the tree |
| `vpc-default-sg-unmanaged` | an `aws_vpc` with no `aws_default_security_group` taking ownership of the group that cannot be deleted |
| `public-lb-without-access-logs` | an `aws_lb` that is not `internal = true` and has no `access_logs` block |
| `kms-key-without-policy` | an `aws_kms_key` with no `policy`, so access is decided entirely elsewhere |
| `log-group-unencrypted` | an `aws_cloudwatch_log_group` with no `kms_key_id` |

A public load balancer on `0.0.0.0/0:443` is normal and is deliberately not a
finding, and neither is an internal load balancer with no access logs. The list is
short for that reason: a guardrail that cries wolf is one people switch off, and the
thirteen that matter go with it. Thirteen checks are a floor, not a security
review — where domain 9a chose Checkov, tfsec, Trivy or Terrascan, the gate runs
that too.

## Suppressing a scanner finding

The scanner the specification chose is noisy at first, and that is expected rather
than a defect: one real stack produced 32 findings, of which 8 were real gaps, 9 were
artefacts of how a Terragrunt stack is composed, and the rest were decisions the
specification had already taken. What matters is that the 8 do not get lost among the
24.

Start from `assets/scanner-config.template.yaml`, put it at the root of the stack,
and keep its convention: **one check id per line, with a reason above it saying which
of three things it is.**

| Category | What it means | Where it is recorded |
|---|---|---|
| False positive | the tool cannot see what the stack does — `CKV2_AWS_5` fires on every security group in a multi-module Terragrunt stack, because it analyses one module at a time | the scanner config, and nowhere else |
| Decided | the specification settled it differently on purpose | a waiver in `discovery-state.json` with the check id in `control`, so the gate matches it; the config file need not mention it |
| Deferred | a real gap, accepted for now | the scanner config **with an owner and a date**, and an open question |

Two checks that contradict each other are worth knowing about before spending an
hour on them: a check requiring an explicit KMS key policy, and the wildcard-action
and wildcard-resource checks, cannot both be satisfied — the account-root statement
AWS requires in every key policy is `kms:*` on `*`. One of the two fires whatever is
written.

Run the scanner **from the stack root**. Every one of these tools discovers its
configuration relative to the working directory rather than to the directory it was
pointed at, so the same stack scanned from one directory up ignores every suppression
in it. `check_iac.py` sets the working directory for you and names the config file
explicitly; a scanner run by hand from the wrong place reports findings that were
reasoned about weeks ago.

## File layout inside a module

One concern per file, and the same five names every time, because a reviewer should
not have to read a directory listing to find where something is:

| File | Holds |
|---|---|
| `versions.tf` | `required_version`, `required_providers`. Nothing else. |
| `variables.tf` | Every input, each typed, described, and validated where a wrong value is expensive. |
| `main.tf` | The resources. Split into `network.tf`, `iam.tf`, `data.tf` when it passes roughly 200 lines — one file per concern, not one file per resource. |
| `outputs.tf` | What a caller needs. Not everything that was created. |
| `locals.tf` | Naming and tagging, where there is enough to warrant its own file. |

## Naming

**One convention, defined once, derived everywhere.**

```hcl
locals {
  name = "${var.project}-${var.environment}"
}
```

Then `"${local.name}-vpc"`, never `"${var.project}-${var.environment}-vpc"` repeated
in forty places. The day the convention changes, it changes once.

**Resource names are `this` when there is one, and descriptive when there are
several.** `resource "aws_vpc" "this"` reads as `aws_vpc.this`; `resource "aws_vpc"
"vpc"` reads as `aws_vpc.vpc`, which says the same word twice. The type is already in
the address.

**Singular resource names, plural only for collections.** `aws_subnet.private`, not
`aws_subnet.private_subnets`.

**Underscores in Terraform identifiers, hyphens in cloud resource names.** That is
the convention both ecosystems already use; mixing them means guessing which is which
at every reference.

## Variables

**Validate what is expensive to get wrong**, not everything:

```hcl
variable "environment" {
  type        = string
  description = "Environment this stack belongs to."

  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "environment must be one of dev, staging or prod."
  }
}
```

A typo caught at plan time costs a second; the same typo applied creates a parallel
set of resources nobody is looking at.

**A default means "this is the right answer for everyone".** Where the specification
settled a value, give it a default. Where it did not, give it none — the plan then
fails loudly instead of provisioning something nobody chose. See rule 6 in `SKILL.md`.

**`sensitive = true` on anything that should not be in CI logs.** It does not keep
the value out of the state file; nothing does.

## Resources

**`for_each` over `count`, unless the thing genuinely is a count.** `count` keys
resources by position, so removing the second of three items destroys and recreates
the third. `for_each` keys them by name, and removing one removes one.

```hcl
resource "aws_subnet" "private" {
  for_each = var.private_subnets      # a map, keyed by availability zone

  vpc_id            = aws_vpc.this.id
  cidr_block        = each.value
  availability_zone = each.key
}
```

`count` is right for `count = var.enable_nat ? 1 : 0` — that really is a number.

**Tags from one merged local, on everything.**

```hcl
locals {
  tags = {
    Project     = var.project
    Environment = var.environment
    ManagedBy   = "terraform"
    Spec        = var.spec_reference
  }
}
```

On AWS, `default_tags` in the provider covers most of it; merge per-resource tags on
top. Someone will find an unexplained resource in the console, and the tag is what
tells them not to delete it.

**`lifecycle { prevent_destroy = true }` on data stores and state buckets.** It costs
nothing until the day it is the only thing between a refactor and an outage.

**`moved` blocks when renaming.** Renaming a resource without one destroys and
recreates it. The block is three lines and can be deleted a release later.

```hcl
moved {
  from = aws_vpc.vpc
  to   = aws_vpc.this
}
```

**No hardcoded region, account, AMI or CIDR.** A region belongs in a variable; an AMI
comes from a `data` source with an owner filter; an account is never written down at
all.

## Data sources over hardcoded values

`data "aws_availability_zones" "available"` rather than a typed list of zone names —
zone names differ per account, and the list goes stale. Same for AMI lookups, caller
identity, and the current partition.

## Outputs

Export what a caller needs, and nothing else. In a Terragrunt stack the callers are
`dependency` blocks in other units, so an output nobody depends on is a maintenance
cost with no reader.

## Terragrunt units

**A unit is thin.** An `include`, a `terraform` block, its `dependency` blocks and its
`inputs`. Logic belongs in the Terraform module, where it can be tested and reused;
a unit that computes things is a module in the wrong place.

**`dependency` blocks with `mock_outputs`**, so `plan` works before the dependency
exists:

```hcl
dependency "network" {
  config_path = "../network"

  mock_outputs                            = { vpc_id = "vpc-mock" }
  mock_outputs_allowed_terraform_commands = ["validate", "plan"]
}
```

Without `mock_outputs_allowed_terraform_commands`, the mock is used at `apply` too,
which is how a mock value reaches real infrastructure.

**No `get_env` without a default in `root.hcl`.** It makes the whole stack fail
`terragrunt hcl validate` on any machine that has not exported the variable — which
is every machine, at the moment the code is being written. Derive the value from
locals the repository already holds, or give the `get_env` a default that is
obviously not a real value.

**One `root.hcl`, included by every unit.** The backend and the provider are generated
there once. A unit that declares either has opted out of the thing Terragrunt is for.

## What not to do, and why it is tempting

| Tempting | Why not |
|---|---|
| A module wrapping one resource | A directory, a variables file and an indirection to save nothing. Write the resource. |
| `terraform_remote_state` between units | Terragrunt `dependency` does this with ordering and mocks. Two mechanisms for one job. |
| Workspaces for environments | One state file, one backend, and a `terraform.workspace` conditional in every resource. Separate directories with separate state are what the specification's environment table already describes. |
| `depends_on` on a module | Almost always means an output should have been passed instead, which expresses the real dependency. |
| A `null_resource` with `local-exec` | It runs on whoever's laptop applied it, and the result is not in state. Usually a sign the work belongs outside Terraform. |
| Committing `.tfvars` with real values | The environment's values belong in `env.hcl` or `inputs`, where the stack can see them; secrets belong in the secret store domain 8 chose. |
